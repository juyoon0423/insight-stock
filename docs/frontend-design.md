# 프론트엔드 디자인 방향과 점검 기록 (2026-11-16)

브랜치 `refactor/frontend-ui`에서 하는 화면 리팩토링의 근거 문서다. **코드를 바꾸기 전에** 정했다.
- 디자인 방향: `frontend-design` 스킬(anthropics/skills)의 절차를 따랐다. 주제를 정하고, 색·글꼴·레이아웃 계획을 세운 다음, "어느 프로젝트에나 나올 기본값이 아닌지" 다시 검토했다.
- 점검: `web-design-guidelines` 스킬(vercel-labs, 규칙 원문 `command.md` 커밋 `4ecfb9f`, 2026-10-05)의 규칙으로 기존 코드를 점검했다.
- 성능 기준선과 측정 조건: [frontend-lighthouse.md](frontend-lighthouse.md)

**범위**: 화면 표현(레이아웃, 색, 글꼴, 컴포넌트 모양, 마크업 접근성)만 바꾼다. 아래 로직은 건드리지 않는다.
- 출처 배지 로직: `citedNumbers`에 있는 번호만 배지로 바꾸고, 범위 밖 번호는 일반 텍스트로 둔다(`lib/citations.ts`).
- 인증 로직: 토큰 저장 위치, `authFetch`의 401 재시도와 refresh 공유, `bootstrapSession`, `tokenStore`.
- 관심 기업 DELETE, 알림 읽음 PATCH 동작.
- Vitest 16개 통과 유지.

## 1. 무엇을 위한 화면인가

- **주제**: DART 공시(금융감독원 전자공시)에 근거해서만 답하는 질문 서비스.
- **사용자**: 공시를 직접 읽기 번거로운 개인 투자자. 포트폴리오로는 면접관, 전시 관람객도 본다.
- **화면이 할 일 하나**: 질문하면 답을 주고, **그 답이 어느 공시에서 나왔는지 바로 확인하게** 한다.

이 서비스의 핵심 가치는 "환각을 줄이고 출처를 보여 주는 것"이다. 그래서 디자인에서 힘을 줄 곳도 하나로 정했다. **답변 속 출처 번호와 출처 목록이 서로 이어져 보이는 것**이다. 나머지는 조용하게 둔다.

## 3. 디자인 방향

### 3-1. 한 줄 콘셉트
**"근거가 붙은 문서"**: 답변을 대화 말풍선이나 카드가 아니라 각주가 달린 문서처럼 보여 준다. 출처 번호는 각주 번호, 출처 목록은 각주 목록이다. 공시 자체가 공문서라는 점에서 가져온 방향이다.

### 3-2. 색 (토큰 이름: 역할)

| `danger` | `#B42318` | `#F29B91` | 오류 | |

색을 고를 때 지킨 원칙은 세 가지다.
- 빨강과 파랑을 "상승·하락"으로 읽는 한국 증시 관례와 헷갈리지 않게 했다. 강조색은 밝은 파랑이 아니라 짙은 군청 하나만 쓰고, 빨강은 오류에만 쓴다.
- 강조색은 **출처와 주요 버튼**에만 쓴다(2026-11-16 "출처에만"에서 고침, 8절). 그러면 화면에서 색이 있는 곳은 "근거가 있는 곳" 아니면 "지금 누를 곳" 둘 중 하나가 된다.
  - 고친 이유: 처음에는 주요 버튼도 강조색이었지만, 입력이 비면 버튼을 비활성(테두리만 남은 회색)으로 바꿨다. 첫 화면에는 늘 빈 입력이 보이므로 주요 행동인 "질문하기"가 꺼진 것처럼 보였다.
  - 주요 버튼은 화면마다 하나뿐이고(질문하기, 검색, 로그인, 회원가입) 모양(채운 사각형)이 출처 배지와 달라서, 같은 색을 써도 "출처"와 헷갈리지 않는다. 예시 질문 같은 보조 동작에는 강조색을 쓰지 않고 중립 배경(`wash`)과 → 표시로 누를 수 있음을 보여 준다.
- 다크 모드는 지금처럼 OS 설정(`prefers-color-scheme`)을 따른다. 같은 토큰 이름에 다크 값만 바꿔 넣는다.

**강조색 하나 원칙의 예외: `/search`의 순위 시각화** (2026-11-16 사용자 결정)
- 하이브리드 검색 화면의 듀얼 마커(`DualRankMarker`)와 매치 패턴 배지(`MatchPatternBadge`, `MatchPatternSummary`)는 **키워드 검색(BM25)과 의미 검색(벡터)을 색으로 구분하는 것 자체가 정보**다. 강조색 하나로 합치면 두 검색이 구분되지 않는다.
- 그래서 이 컴포넌트들에만 데이터 구분용 색 2개를 따로 둔다: `rank-keyword`(지금의 파랑 계열), `rank-vector`(지금의 주황 계열). 두 색은 출처 강조색(`evidence`)과 헷갈리지 않게 밝기와 색상을 다르게 정하고, 구현할 때 대비를 확인해 5절 표에 추가한다.
- 색만으로 구분하지 않는다는 원칙은 지금 그대로다. 범례 글자("키워드", "의미")와 배지 문구가 이미 있다.

### 3-3. 글꼴

| 후보 | 장점 | 단점 | 결정 |
|---|---|---|---|
| OS 기본 글꼴 유지 | 추가 다운로드 0 | OS마다 모양이 다르다. README 캡처(맥)와 윈도 사용자 화면이 다르다 | 대안으로 보류 → **최종 채택**(아래 "측정 후 결정") |
| Pretendard | 한국 서비스에서 가장 많이 쓰고 깔끔하다 | `next/font/google`에 없어서 npm 패키지나 CDN을 새로 들여야 한다. 너무 흔해서 개성이 없다 | 제외 |
| Noto Sans KR | 안정적이고 `next/font/google`에 있다 | 구글 기본 한글 글꼴이라 개성이 거의 없다 | 제외 |
| **IBM Plex Sans KR** | `next/font/google`에 있어서 자체 호스팅되고 한글은 쓰는 글자 구간만 받는다. 기술 문서와 보고서를 염두에 둔 글꼴이라 "공시 문서" 콘셉트와 맞는다. 숫자(계약금액 `700,000,000,000원` 등)가 또렷하다 | 한글 글꼴이라 용량이 크다 | **선택** |

- 글꼴은 **한 가족만** 쓴다. `next/font/google`로 **400, 600 두 굵기만** 불러온다(굵기가 늘면 내려받을 파일도 늘어난다). 제목용 글꼴을 따로 두지 않는다. 지금 쓰는 `font-bold`(700)와 `font-medium`(500)은 각각 600, 400으로 맞춘다. 브라우저가 없는 굵기를 흉내 내지 않게 하기 위해서다.
- 금액과 숫자에는 `tabular-nums`를 적용해 자릿수를 맞춘다.
- 크기 단계는 본문 16px(지금 답변 본문과 같음), 보조 14px, 메타 13px, 페이지 제목 24px, 서비스 이름 20px로 둔다. 지금 12px(`text-xs`)과 11px(`text-[11px]`)로 쓰는 작은 글자는 13px 이상으로 올린다.
- 쓰지 않는 Geist, Geist Mono는 뺀다.
- **성능 조건**: 바꾼 뒤 Lighthouse에서 LCP가 기준선보다 0.2초 넘게 늘거나 CLS가 0.05를 넘으면, IBM Plex Sans KR을 빼고 OS 기본 글꼴 스택으로 되돌린다. 이 판단도 결과와 함께 기록한다.

**측정 후 결정 (2026-11-16): IBM Plex Sans KR을 빼고 OS 한글 글꼴 스택으로 되돌렸다.**
- IBM Plex Sans KR(400, 600)을 `next/font/google`로 넣고 같은 조건으로 쟀다. 그 결과 글꼴 파일이 페이지마다 약 100개(약 900KB) 내려왔다. 한글은 글자 구간별로 파일이 쪼개져 있어서, 한 화면에 나온 글자만으로도 구간 수십 개를 굵기마다 받기 때문이다.
- 모바일 `/`의 LCP가 3회 중 2회 약 8.95초가 나왔다(중앙값 8.95초, 기준선 0.76초). Performance 점수도 75/100/75였다. LCP 요소는 제목 아래 설명 문단이다. `font-display: swap`으로 먼저 OS 글꼴로 그린 뒤, 느린 4G에서 웹폰트가 다 도착하면 글자를 다시 그리고 그 시점이 LCP로 다시 기록됐다.
- 되돌림 기준(LCP +0.2초 초과)을 넘었으므로 미리 정한 대로 되돌렸다. 최종 스택: `-apple-system, BlinkMacSystemFont, "Apple SD Gothic Neo", "Malgun Gothic", "Noto Sans KR", system-ui, sans-serif`
- 웹폰트로 얻으려던 것 중 남긴 것: 400과 600 두 굵기만 쓰는 크기 단계, 숫자의 `tabular-nums`, 최소 13px. OS마다 모양이 조금 다르다는 단점은 받아들였다.
- 측정 원본은 `lighthouse-reports/after-plex-kr/`(저장소 밖)에 있고, 수치는 [frontend-lighthouse.md](frontend-lighthouse.md) 3절에 있다.

**답변 화면, 좁은 화면**: 본문 아래에 각주 목록이 이어진다(지금과 같은 순서).

**이 디자인에서 기억에 남을 한 가지**: 답변 속 번호 ①을 누르면 해당 출처로 이동하면서 그 출처에 `evidence-tint` 배경이 칠해진다.
- **지금 동작(코드로 확인)**: 배지는 `<a href="#source-N">`(`components/AnswerText.tsx`)이고, 출처는 `id="source-N"`인 `<a>`(`components/SourceCard.tsx`)다. 브라우저 기본 앵커 이동이라 JavaScript가 없다. 부드러운 스크롤(`scroll-behavior`)도 없이 즉시 이동하고, 주소 끝에 `#source-N`이 붙으며, 대상 위에 `scroll-mt-24`(96px) 여백을 둔다.
- **바꾸는 것**: 위 동작은 그대로 유지하고(즉시 이동, 해시 갱신, 96px 여백), CSS `:target` 선택자로 대상 출처에 배경색만 더한다. JavaScript와 스크롤 방식은 바꾸지 않는다.
- 넓은 화면의 2단 레이아웃에서도 출처는 문서 흐름 안에 있다(`position: sticky`를 쓰지 않음). 그래서 앵커 이동 위치 계산이 지금과 같다.
- 이 화면에서 쓰는 움직임은 이것 하나다. 사용자가 누른 동작에 대한 반응이고, `prefers-reduced-motion`이면 색 전환 애니메이션 없이 바로 표시한다.

**출처 목록**: 둥근 카드 2열 반복을 그만두고, 왼쪽 선과 번호가 있는 목록으로 바꾼다. 출처는 순서(1, 2, 3)가 실제 의미를 가지는 정보라 번호 표시가 정당하다.

**"찾지 못했습니다" 상태**: 지금의 점선 상자와 🔍 이모지 대신, 거절 이유와 **다음에 할 일**(회사명과 사건을 넣어 묻기, 수집 기간 확인)을 문장으로 보여 준다. 문구는 기존 내용을 유지하고 다음 행동 한 줄만 더한다.

### 3-5. 기본값 점검 (frontend-design 절차의 2차 검토)

계획을 세운 뒤 "비슷한 서비스를 만들면 자동으로 나올 기본값"과 겹치는지 다시 봤다. 바꾼 것은 아래와 같다.
- **출처를 둥근 카드 그리드로 두기** → 흔한 SaaS 카드 구성이라 각주 목록으로 바꿨다.
- **접수번호를 모노스페이스 글꼴로 표시하기**(처음 떠올린 안) → "작은 데이터 라벨에 모노 글꼴"도 흔한 기본값이다. 같은 글꼴에 `tabular-nums`만 적용하는 것으로 바꿨다.
- **헤더 위 작은 대문자 라벨("ANSWER", "SOURCES")** → 쓰지 않는다. 한국어 화면에 영어 대문자 라벨은 정보가 없다.
- **배경 그라데이션, 섹션별 등장 애니메이션** → 쓰지 않는다. 움직임은 3-4의 출처 표시 하나뿐이다.
- 그대로 둔 것: 헤더 아래 구분선 1개. 로그인 상태와 본문을 나누는 실제 정보라서 유지한다.

### 6-1. 출처의 접수일: 이번에는 표시하지 않는다
- 사용자 기준: "`sources` 응답에 있으면 표시하고, 백엔드 수정이 필요하면 뺀다."

| 같은 섹션 출처 구분 표시 | 백엔드 `SourceRef`(청크 순번 등) + `components/SourceCard.tsx` | 한 공시의 같은 섹션에서 청크가 여러 개 인용되면 출처가 회사명·보고서명·섹션명까지 똑같이 보여 중복처럼 보인다(받아 둔 q6의 출처 1·3, q5의 출처 2건 모두 해당). 구분하려면 응답에 청크를 가리키는 값(순번, 발췌 등)이 있어야 해서 백엔드 수정이 필요하다. 홈 미리보기는 q5도 겹쳐서 q6을 그대로 쓴다 |

### 홈 첫 화면 수정 (2026-11-16, 사용자 피드백)
구현한 홈을 직접 본 뒤 "와이어프레임처럼 보인다"는 피드백을 받았다. 지적한 이유 네 가지와 고친 내용이다.

| 문제 | 원인 | 고친 내용 |
|---|---|---|
| 헤더는 넓은데 본문은 왼쪽 2/3에서 끝나 오른쪽이 비어 보인다 | 헤더와 `<main>`은 `max-w-5xl`인데 홈 본문만 다시 `max-w-2xl`로 감쌌다 | 본문도 헤더와 같은 폭을 쓰고, 넓은 화면(1024px 이상)에서는 2단(`1fr` + `20rem`)으로 나눴다. 헤더 오른쪽 끝과 미리보기 카드 오른쪽 끝이 1208px로 맞는다(1440px 화면) |
| "질문하기"가 회색 테두리라 비활성처럼 보인다 | 빈 입력이면 버튼을 비활성으로 만들고, 비활성 스타일을 테두리만 남게 정했다 | 버튼은 늘 군청 채움. 빈 입력·공백만 입력하고 누르면 API를 부르지 않고 입력창으로 포커스만 옮긴다. 비활성은 답변 생성 중에만(채움 유지, 불투명도 0.7) |
| 핵심인 출처 배지가 첫 화면에 안 보인다 | 배지는 답변이 나와야 보였다 | 오른쪽 칸에 정적 "답변 미리보기" 카드. 실제로 받은 q6 응답에서 문장과 숫자를 그대로 가져왔다(첫 문단 전체 + 둘째 문단의 한 문장, 생략은 "…"). 배지는 실제 답변과 같은 `.cite-badge` 모양이고 같은 `splitAnswerByCitations`로 나눈다. 링크가 아닌 표시용이다. 질문을 하면 카드를 숨긴다 |
| 예시 질문이 누를 수 있는 항목으로 안 보인다 | 줄 목록에 hover 표시가 거의 없었다(`surface`는 바탕과 거의 같은 흰색) | hover 때 중립 배경(`wash`)과 오른쪽 `→`(화면 낭독기에서는 숨김)가 진해지며 살짝 이동 |

- 좁은 화면 순서: 입력창 → 예시 질문 → `/search` 링크 → 미리보기. 예시 질문이 첫 화면에 보이게 하려는 것이다. Pixel 7(412×839)에서 예시 질문 4개의 아래 끝이 712px로 첫 화면 안에 든다.
- 빈 입력 확인(Playwright, 녹화 응답만 사용): 빈 입력 클릭, 공백 4칸 클릭, 공백+탭 Enter 세 경우 모두 `/api/v1/answers` 요청 0회, 포커스가 `#question`으로 이동, 미리보기는 그대로 보였다.
- 헤더 알림 아이콘은 이모지가 아니라 SVG(`NotificationBell.tsx`, `aria-hidden`)인 것을 확인했다.
- 같은 버튼 스타일을 쓰는 `/search` 검색 버튼은 빈 입력일 때 비활성 규칙을 그대로 두었다(이번 범위 밖). 이제 비활성 모양이 "흐린 군청 채움"이라 꺼진 테두리로 보이지는 않는다.
- Lighthouse `/` 재측정과 캡처: [frontend-lighthouse.md](frontend-lighthouse.md) 3-5절.

### 한글 줄바꿈과 배지 줄 간격 (2026-11-16, 사용자 피드백)
| 문제 | 원인 | 고친 내용 |
|---|---|---|
| 한글이 단어 중간에서 끊긴다("-30,041백/만원", "증가하였습니/다") | 브라우저 기본 줄바꿈은 한글을 글자 단위로 끊는다 | 답변 본문, 미리보기, 출처 목록에 `word-break: keep-all`(어절 단위 줄바꿈)과 `overflow-wrap: anywhere`(칸보다 긴 숫자·영문만 강제로 끊음). Tailwind `break-keep wrap-anywhere` |
| 배지가 있는 줄만 줄 간격이 벌어진다 | 배지를 `vertical-align: super`로 올려서, 배지 위쪽이 줄 높이 밖으로 나가 그 줄만 높아졌다 | 배지 `line-height: 1`, 위로 올리는 것은 `position: relative; top: -0.25rem`(줄 높이 계산에 영향 없음) |
| (고치면서 생긴 문제) 배지만 다음 줄로 떨어진다("…않았습니다 / [3].") | `keep-all`로 어절 단위로 끊기 시작하자, 원자 인라인(`inline-flex`)인 배지 앞이 줄바꿈 지점이 됐다 | 본문 속 배지는 일반 인라인(`.cite-badge-inline`, `display: inline`)으로 바꿨다. `keep-all`이 글자와 숫자 사이 줄바꿈을 막아 배지가 앞 단어에 붙어 다닌다. 높이는 위아래 padding으로 약 20px를 맞췄다. 출처 목록의 번호 배지는 그대로 `inline-flex` |

- 측정(Playwright, 녹화한 q5·q6 응답 재생, 데스크톱 1440px와 Pixel 7): 글자마다 위치를 재서 줄을 나눴다.
  - 줄 간격: 미리보기 25~26px(14px × 1.8 = 25.2px), 답변 본문 31~32px(17px × 1.85 = 31.45px)로 배지가 있는 줄도 같다. 50px, 63px는 문단 사이 빈 줄(두 줄 높이)이다.
  - 단어 중간 끊김 0건(미리보기, 답변 본문, 출처 목록), 앞 글자와 다른 줄로 떨어진 배지 0건.
- 미리보기 출처 1과 3이 같은 섹션으로 보이는 문제는 q5 응답(출처 2건 모두 "정 정 신 고 (보고)")도 같아서 q6을 유지하고, 7절 별도 작업 목록에 "같은 섹션 출처 구분 표시"로 넣었다.

### 브라우저로 확인한 핵심 흐름 (2026-11-16, 리팩토링 후 프로덕션 빌드)
- 조건: 로컬 백엔드를 `--scheduling.enabled=false`로 띄웠다(수집·알림 감지 배치 꺼짐). 기존 계정은 쓰지 않고, 화면의 회원가입 폼으로 테스트 계정 `demo@example.com`(닉네임 "데모")을 새로 만들었다. 비밀번호는 문서에 남기지 않는다. 브라우저 조작은 Playwright(설치된 Chrome)로 했다.

| 흐름 | 결과 | 확인한 근거 |
|---|---|---|
| 회원가입 | 통과 | `POST /api/v1/auth/signup` → 201, 메인으로 이동, 헤더에 "데모님" |
| 로그아웃 → 로그인 | 통과 | 헤더가 "로그인" 링크로 바뀜 → `POST /api/v1/auth/login` → 200, 헤더 "데모님". localStorage에는 `insightstock.refreshToken`, `insightstock.user`만 있다(access token은 메모리) |
| 새로고침 후 로그인 유지 | 통과 | 새로고침 직후 `POST /api/v1/auth/refresh` → 200, 헤더 "데모님" 유지(`bootstrapSession`) |
| 관심 기업 추가 | 통과 | 신한지주, 코아스 검색 후 선택 → `POST /api/v1/watchlist` → 201 두 번, 목록에 2건 |
| 관심 기업 삭제 | 통과 | 코아스 "삭제" → `DELETE /api/v1/watchlist/{id}` → 204, 목록 1건. 새로고침 후에도 1건 |
| 알림 목록 열기 | 통과 | 알림 버튼 `aria-expanded="true"`, `GET /api/v1/notifications` → 200 |
| 알림 읽음(PATCH) | **미확인** | 새 계정에는 알림이 없다("아직 알림이 없습니다."). 알림은 감지 배치가 만들기 때문에, 배치를 켜지 않기로 해서 확인하지 못했다. 읽음 처리 코드(`NotificationBell.handleItemClick`)는 클래스와 `aria` 속성만 바꿨고 로직은 그대로다 |

- 이 확인으로 로컬 DB에 `users` 1행(demo@example.com)과 `watchlist` 1행(신한지주)이 남았다. 공시 건수는 6,188건 그대로다.
