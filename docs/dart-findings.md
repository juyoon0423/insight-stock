# OpenDART API 탐색 기록

Open DART API(`https://opendart.fss.or.kr/api`)의 "공시검색"(list)과 "공시원문"(document)
API를 실제로 호출해보며 확인한 응답 구조와 함정, 그리고 이후 RAG 파이프라인을 만들 때
고려할 청킹 전략을 정리한다.

## 1. 응답 구조

### 1-1. list API (`GET /api/list.json`)

공시 목록을 조회한다.

**주요 요청 파라미터**
- `crtfc_key` (필수): 발급받은 인증키
- `corp_code`: 특정 회사만 조회 (생략 시 전체 회사)
- `bgn_de`, `end_de`: 조회 기간 (생략 시 최근 기간 기본값 적용)
- `page_no`, `page_count`: 페이징
- `sort`, `sort_mth`: 정렬 기준/방향 (예: `date`, `desc`)

**응답 구조**
```json
{
  "status": "000",
  "message": "정상",
  "page_no": 1,
  "page_count": 10,
  "total_count": 123,
  "total_page": 13,
  "list": [
    {
      "corp_code": "01786958",
      "corp_name": "큐리오시스",
      "stock_code": "494120",
      "corp_cls": "K",
      "report_nm": "임원ㆍ주요주주특정증권등소유상황보고서",
      "rcept_no": "20260721000162",
      "flr_nm": "허대성",
      "rcept_dt": "20260721",
      "rm": ""
    }
  ]
}
```

**주요 필드**
- `status` / `message`: 응답 코드. `000`이 정상, 그 외는 에러(§2-1 참고)
- `rcept_no`: 접수번호. document API 호출 시 핵심 키
- `report_nm`: 공시 유형명. 원문 존재 여부/문서 크기를 가늠하는 힌트가 됨 (§3 참고)
- `corp_code` / `corp_name` / `stock_code`: 회사 식별 정보
- `corp_cls`: 법인구분 (K=코스닥, Y=유가증권, N=코넥스, E=기타)
- `rm`: 비고 (코스닥/유가증권 표시 등)

### 1-2. document API (`GET /api/document.xml`)

특정 공시 1건의 원문을 내려받는다.

**요청 파라미터**
- `crtfc_key` (필수)
- `rcept_no` (필수): list API에서 얻은 접수번호

**응답 형식**
- 정상일 때: **ZIP 파일** (Content가 `PK\x03\x04`로 시작). 내부에 `{rcept_no}.xml` 파일 하나가 들어있음 (UTF-8 인코딩)
- 실패일 때: ZIP이 아니라 순수 XML 에러 응답. 예:
  ```xml
  <?xml version="1.0" encoding="UTF-8" standalone="yes"?><result><status>014</status><message>파일이 존재하지 않습니다.</message></result>
  ```

**내부 XML 구조 (DART 자체 스키마, `dart4.xsd`)**
```xml
<DOCUMENT xmlns:xsi="..." xsi:noNamespaceSchemaLocation="dart4.xsd">
  <DOCUMENT-NAME ACODE="...">임원ㆍ주요주주 특정증권등 소유상황보고서</DOCUMENT-NAME>
  <FORMULA-VERSION ADATE="...">6.1</FORMULA-VERSION>
  <COMPANY-NAME AREGCIK="...">주식회사 큐리오시스</COMPANY-NAME>
  <SUMMARY>...</SUMMARY>
  <BODY ATOCID="...">
    <TITLE ATOC="Y" ...>...</TITLE>
    <TABLE ACLASS="NORMAL" ...>
      <TBODY>
        <TR><TD>...</TD><TD>...</TD></TR>
      </TBODY>
    </TABLE>
    ...
  </BODY>
</DOCUMENT>
```
표준 HTML이 아니라 DART가 정의한 태그 체계(`TITLE`, `TABLE`/`TBODY`/`TR`/`TD`, `P`, `SPAN` 등)로
공시서식 레이아웃(표, 문단, 강조)을 표현한다.

## 2. 발견한 함정들

### 2-1. `status: "014"` — 원문이 없는 공시 유형

일부 `report_nm`(예: 임원·주요주주 소유상황보고서 중 특정 건)은 document API로 원문을 주지 않고
ZIP 대신 아래와 같은 XML 에러를 반환한다.

```xml
<result><status>014</status><message>파일이 존재하지 않습니다.</message></result>
```

**대응**: document API 호출 후 응답이 ZIP인지 먼저 확인(`zipfile.is_zipfile`)하고, 아니면
`<status>014</status>` 포함 여부로 "원문 없음"을 구분해 건너뛰어야 한다. list에서 얻은 rcept_no를
무조건 성공한다고 가정하면 안 된다.

### 2-2. DART XML이 항상 well-formed하지는 않음

투자설명서(`report_nm: 투자설명서(일괄신고)`, rcept_no `20260721000155`) 문서를
`xml.etree.ElementTree`로 파싱하면 에러가 발생한다.

```
xml.etree.ElementTree.ParseError: mismatched tag: line 3620, column 157
```

원인을 확인해보니 본문 텍스트 안에 이스케이프되지 않은 `<` 문자가 그대로 들어있었다.

```
<P USERMARK="F-GL "><표1>신용환산율</P>
```

`<표1>`이 실제로는 서술형 텍스트의 일부("<표1> 참고")인데, 파서는 이를 태그로 오인해서
이후 태그 매칭이 전부 어긋난다. 즉 DART가 "XML"이라 부르지만 실제로는 완전히
well-formed한 XML이 아닌 문서가 섞여 있다.

**대응**: 엄격한 `xml.etree.ElementTree` 단독 사용은 위험하다.
- `lxml`의 `recover=True` 파서로 관대하게 파싱하거나
- 파싱 실패 시 정규식 기반 태그 제거(`re.sub(r"<[^>]+>", ...)`)로 폴백하는 등
파싱 실패를 전제로 한 방어적 처리가 필요하다.

### 2-3. 문서 크기 편차가 매우 큼

같은 "원문 텍스트 추출" 작업이어도 문서 유형에 따라 결과 크기가 크게 다르다.

| 문서 | XML 크기 | 태그 제거 후 텍스트 길이 |
|---|---|---|
| 임원·주요주주 소유상황보고서 (`20260721000160`) | 25,756 bytes | 1,591자 |
| 투자설명서(일괄신고-사채) (`20260721000155`) | 697,651 bytes | 123,413자 |

약 80배 차이. 정형 서식(소유상황보고서 등)은 태그 오버헤드가 실제 텍스트보다 커서 결과가
작고, 서술형 문서(투자설명서, 사업보고서류)는 리스크 고지 등 방대한 텍스트를 포함한다.
고정된 처리 방식(예: 한 문서 = 한 청크)으로는 대응할 수 없다.

### 2-4. 표를 단순 태그 제거하면 라벨-값 관계가 깨짐

`"".join(element.itertext())`처럼 텍스트만 단순 추출하면, 표의 각 셀 값이 줄 단위로
나열될 뿐 어떤 라벨에 어떤 값이 붙는지 알 수 없게 된다.

```
회 사 명
주식회사 큐리오시스
법인구분
코스닥상장법인
```

`TABLE` → `TR` → `TD` 단위로 순회하며 같은 행의 셀을 `" | "` 등으로 재조합하면
라벨-값 관계가 어느 정도 복원된다.

```
보고자 : | 윤호영
```

다만 셀 내부에 줄바꿈이 여러 개 포함된 경우(여러 항목이 한 셀에 세로로 나열)에는
이 방식도 완벽하지 않고 후처리가 더 필요하다.

### 2-5. 정규식 폴백 경로가 실제로 ~30% 발동하며, 섹션 마커와 표 구조를 동시에 잃는다

2026-07-22 청킹 작업 착수 전 실제 배치(20건)로 검증한 결과, `XmlTextExtractor`의 엄격
DOM 파싱이 6/20(30%)에서 실패하고 정규식 폴백(`regexStrip`, `<[^>]+>` 제거)으로
넘어갔다. `docs/progress.md`가 "미검증"으로 남겨뒀던 경로가 실제로 이 정도 비율로
발동한다는 뜻이라 무시할 수 없는 크기다. 실패 원인은 대부분:

- `<meta>` 같은 미종료 태그
- 이스케이프 안 된 `&`로 인한 엔티티 참조 오류(예: `"I"`, `"T"`, `"P500"` 엔티티가
  `;`로 안 끝남 — 본문에 `R&D`, `P500` 같은 표현이 그대로 들어간 것으로 추정)
- 2-2에서 이미 확인한 `<표1>` 같은 가짜 태그(`</표1>` 종료 태그 불일치)

폴백은 청킹을 염두에 두고 만든 게 아니라서, 청킹에 필요한 정보 두 가지를 동시에 잃는다.

1. **섹션 마커 소실**: `TITLE` 요소가 있었다는 사실 자체가 사라진다. 청킹을 위해
   `XmlTextExtractor`에 추가한 `[[SECTION]]` 마커(4절 참고)도 이 경로에서는
   당연히 생기지 않는다.
2. **표 라벨-값 구조 소실**: `appendTableRows()`의 `"셀1 | 셀2"` 행 조합을 거치지
   않고 `TD` 셀 텍스트가 한 줄씩 그대로 남아, 2-4에서 고친 문제가 재현된다.

실측 사례(`rcept_no=20260721000005`, 투자설명서): DOM 경로였다면 표로 압축됐을
계열사·펀드 목록이 정규식 경로에서는 "회사명\n사업자번호\n\n회사명\n사업자번호\n..."
형태로 한 줄씩 풀려서, char_length가 786,390자(이 표에서 관측된 기존 최대치
123,413자의 약 6배)까지 늘어났다. 내용 자체는 진짜 데이터(계열사 목록, 투자조합
현황)이지 깨진 값은 아니었지만, 이 상태로 슬라이딩 윈도우로 자르면 라벨과 값이
서로 다른 청크로 갈릴 위험이 크다.

**대응(1차, 2026-07-22 오전)**: 폴백 자체를 고치는 대신 청킹 단계에서 `[[SECTION]]`
마커 유무로 전략을 분기했다(4절, `chunks.chunk_source` 참고) — 마커가 없는 문서는
"구조를 모른다"는 걸 인정하고 슬라이딩 윈도우만 적용한다.

**대응(2차, 같은 날 오후)**: "원본 XML이 깨져 있어 정확도를 보장할 수 없다"는
전제 자체를 다시 검증해보니, 실제로는 이스케이프 안 된 `&`와 가짜 태그 두 가지
패턴이 원인의 대부분이었고 둘 다 복구 가능했다 — 2-7절 참고. 폴백을 아예 안 타게
만드는 쪽으로 방향을 바꿨다.

### 2-6. 일부 "자율공시"는 DART4 스키마가 아니라 HTML 보일러플레이트 — CSS가 그대로 청크에 남음

지금까지 문서 전체가 DART4 XSD(`<DOCUMENT>`/`TITLE`/`TABLE`) 스키마라고 가정했는데,
2026-07-22 SLIDING_WINDOW 청크를 직접 열어보다가 예외를 발견했다. 원본 XML을 다시
받아보니 일부 "자율공시" 유형(`report_nm` 예: 기업설명회(IR)개최(안내공시), 유상증자
또는 주식관련사채등의청약결과(자율공시), 최대주주등소유주식변동신고서, 단일판매·공급계약체결
등 — 특정 report_nm 하나가 아니라 여러 유형에 걸쳐 있음)은 완전히 다른 구조다:

```html
<html>
 <head>
  <meta content="gdi" http-equiv="X-UA-TextLayoutMetrics">
  <meta content="text/html; charset=euc-kr" http-equiv="Content-Type">
  <STYLE>
.xforms * { font-family: 돋움체;}
.xforms table { font-size: 10px; ... }
  </STYLE>
  <title>...</title>
 </head>
 <body>
  <div class="xforms"> ... <table><tbody><tr><td>...</td></tr></tbody></table> ...
 </body>
</html>
```

DART4 스키마의 대문자 `TITLE`/`TABLE`/`TR`/`TD`와 달리 소문자 HTML 태그(`table`,
`tr`, `td`)를 쓰고, `<meta>`처럼 자체 종료 안 되는 HTML void element가 섞여 있어
엄격 XML 파싱이 항상 실패한다(2-3의 "meta 태그 미종료" 에러가 바로 이 유형).
문제는 그 다음: 정규식 폴백(`<[^>]+>` 제거)은 태그만 지우지 `<STYLE>...</STYLE>`
**안의 CSS 텍스트**는 태그가 아니라서 그대로 남는다. 실측(`rcept_no=20260721800091`,
2,380자): 청크 4개 중 2개(약 67%)가 `color: #194866; text-decoration: none;` 같은
순수 CSS였다 — 진짜 공시 내용이 아니라 완전한 노이즈.

기존에 저장된 데이터 전체를 조회해보니 이 유형이 드문 예외가 아니었다: `PARSED`/
`CHUNKED` 59건 중 **18건(30.5%)**의 `raw_content`에 CSS 흔적(`.xforms`, `font-size`,
`padding` 등)이 남아 있었다.

**대응**: `XmlTextExtractor.regexStrip()`이 일반 태그 제거 전에 `<head>`/`<style>`/
`<script>` 블록을 내용째로 먼저 잘라내도록 수정(대소문자 무관, 백레퍼런스로 여는/닫는
태그 이름이 일치할 때만 매치). 18건 재정제 후 CSS 흔적 0건으로 확인. HTML 주석
(`<!--...-->`)은 이미 기존 `<[^>]+>` 규칙으로 잘 지워지고 있어 별도 처리 불필요함을
확인(내용에 `>`가 없는 한 주석 전체가 하나의 "태그"처럼 매치되기 때문).

**참고(현재는 영향 없음, 나중에 파서를 관대하게 바꾸면 재검토)**: 이 HTML 유형은
`TABLE`/`TITLE`이 아니라 소문자 `table`/`title`을 쓴다. `XmlTextExtractor.walk()`의
`TITLE`/`TABLE` 분기와 `appendTableRows()`의 `getElementsByTagName("TR")`는 지금
전부 대소문자 무관(`equalsIgnoreCase`) 또는 그렇지 않은 조합이 섞여 있는데, 이 유형은
애초에 DOM 파싱까지 도달하지 못해(항상 폴백) 지금은 문제가 되지 않는다. 나중에
`lxml recover`처럼 더 관대한 파서로 바꿔서 이 유형도 DOM 경로를 타게 되면, HTML의
`<title>`(페이지 제목, 섹션 아님)이 `[[SECTION]]` 마커로 잘못 잡히지 않는지 다시
확인해야 한다.

### 2-7. 정규식 폴백이 조문 인용 표기(`<개정 2009.2.3>` 등)를 태그로 오인해 삭제하고 있었다 — 데이터 손실

2-5의 "폭증" 문제를 파고들다가 원본 XML을 다시 열어봤는데, 예상과 다른 걸 발견했다.
`SLIDING_WINDOW`가 큰 문서(`rcept_no=20260721000005`, 투자설명서)의 파싱 실패 원인이
"NICE P&I"의 `&`(이스케이프 안 된 앰퍼샌드)였다. 이걸 고치고 다시 파싱했더니 **다른
곳에서 또 실패**했는데, 이번엔 이런 텍스트였다.

```
제9조 (그 밖의 용어의 정의) ... 다만, 전문투자자 중 대통령령으로 정하는 자가 ...
<개정 2009.2.3>1. 국가2. 한국은행3. 대통령령으로 정하는 금융기관...
```

`<개정 2009.2.3>`은 한국 법령 조문에서 개정 이력을 표기하는 관용구(2-2의 `<표1>`과
같은 패턴)인데, XML 파서는 이걸 태그로 인식해서 매칭 실패로 처리한다. **더 중요한
건**: 이 텍스트가 실패했을 때 타는 기존 정규식 폴백(`<[^>]+>` 제거)은 `<개정
2009.2.3>`을 "닫는 태그가 없는 열린 태그"가 아니라 **완결된 하나의 `<...>` 태그로
인식해서 통째로 삭제**한다. 즉 이 문서가 정규식 폴백을 탈 때마다 실제 조문 인용
내용이 조용히 사라지고 있었다 — 파싱 에러(눈에 보임)와 달리 이건 **에러 없이 발생하는
데이터 손실**이라 더 위험했다.

**대응**: `XmlTextExtractor.extract()`에 3단계 파싱을 도입했다.
1. 엄격 파싱(기존과 동일)
2. 실패 시 정제(이스케이프 안 된 `&` → `&amp;`, "ASCII 문자로 시작하는 태그명"
   패턴에 안 맞는 `<...>`는 `&lt;`/`&gt;`로 이스케이프 — 한글이 섞인 `<표1>`,
   `<개정 2009.2.3>`, `<자본시장과 금융투자업에 관한 법률>` 등은 이 패턴에 애초에
   안 걸려 안전하게 "가짜 태그"로 판별됨) 후 재시도. 성공하면 DOM 경로(표 압축 +
   섹션 마커)를 그대로 탄다.
3. 그래도 실패하면(HTML 보일러플레이트 등, 2-6) 기존 정규식 폴백으로 최종 하강.

**실측 검증** (`backend/src/test/java/.../XmlTextExtractorTest.java`에 회귀
테스트로도 남김):
- 786,390자 문서(`20260721000005`): 파싱 성공, `TABLE` 2,944개·`TITLE` 64개 복구.
  기존 `PARSED`/`CHUNKED` 121건을 재정제+재청킹한 결과:
  - 폴백(마커 없음) 비율 42.1% → **12.5%**
  - 이 문서의 "표 나열형"(줄 평균 15자 미만) 청크 비율 72.1% → **3.6%**
  - char_length는 786,390 → 898,165자로 오히려 늘었다 — 나쁜 신호가 아니라
    `appendTableRows()`가 `" | "` 구분자를 명시적으로 넣고, 전에는 삭제되던
    법령 인용 텍스트가 이제 보존되기 때문. **"청크 개수/글자 수"가 아니라
    "표 구조가 살아있는 비율"이 원래 문제였다는 게 이번에 드러났다.**
- 남은 `SLIDING_WINDOW`(정제로도 복구 안 되는 문서)는 21개 청크뿐이라, 원래
  검토하던 "폴백에서도 표 압축" 작업은 보류하기로 했다(progress.md 참고).

### 2-8. Nori 기본 사전이 이 도메인에서 제일 중요한 단어 "보고서"를 깨뜨리고 있었다

ElasticSearch 색인 설계 단계에서(2026-07-22), 코드를 짜기 전에 실제 청크 내용을
`_analyze` API로 먼저 테스트해봤다. Nori(`analysis-nori`) 자체는 압도적으로
유효했다 — 표준(standard) 분석기와 비교하면 차이가 확연하다.

```
표준 분석기: "금일nxt경쟁매매대상종목지정으로인한krx시간외단일가매매제외종목안내"
             (사실상 하나의 덩어리, 검색 불가)
nori 분석기: 기타 | 시장 | 안내 | 금일 | nxt | 경쟁 | 매매 | 대상 | 종목 | 지정 | ...
             (실제 검색어 단위로 분리됨)
```

그런데 이 도메인에서 가장 많이 검색될 단어인 **"보고서"가 기본 사전으로는 깨진다**는
걸 발견했다.

```
"소유상황보고서를 제출..." → 소유 | 상황 | 보          ("고서"가 통째로 소실)
"감사보고서 (2025.12)"    → 감사 | 보고 | 서 | ...
```

원인을 `nori_tokenizer`만 단독으로 돌려서(필터 없이) 확인해보니, **토크나이저
자체가** "보고서"를 사전에 없는 단어로 보고 "보"+"고서"로 잘못 분해하고 있었다.
"고서"는 이후 `nori_part_of_speech` 필터가 연결어미로 오인해서 제거해버린다 —
파싱 에러처럼 눈에 보이는 게 아니라 **검색이 조용히 안 되는** 종류의 문제라
2-7의 데이터 손실 사례와 성격이 비슷하다.

비슷한 패턴을 다른 후보 단어들에서도 찾았다:
- `특수관계인` → `특수 | 관계 | 이 | ᆫ` (`ᆫ`은 자모 하나만 남은 완전한 가비지 토큰)
- `감사인` → `감사 | 이 | ᆫ` (동일 패턴 — "~인"(人) 접미사가 계사 "이다"의 활용형으로
  오분석됨)
- `이사회` → `이 | 사회` (더 심각함 — "이사회"(理事會, board)가 아니라 "이"+"사회"
  (社會, society)로 쪼개져서 **의미가 완전히 다른 단어**가 됨)

반면 사용자가 후보로 제안한 다른 용어들(`유상증자`→`유상`+`증자`, `최대주주`→
`최대`+`주주`, `자기주식`→`자기`+`주식` 등)은 분해돼도 각 조각이 여전히 의미
있고 검색 가능해서 사전에 추가하지 않았다 — 사전은 "완전히 깨지는" 경우에만
최소로 추가하는 게 유지보수에 유리하다고 판단.

**대응**: `nori_tokenizer`에 `decompound_mode: mixed` + `user_dictionary_rules`
6개(`보고서`/`신고서`/`설명서`/`특수관계인`/`감사인`/`이사회`)를 등록. 흥미로운
점: `report_nm`에서 뽑은 복합어 18개를 전부 개별 등록할 필요 없이, 공통 접미사
3개(`보고서`/`신고서`/`설명서`)만 등록하면 `decompound_mode: mixed`가 "소유상황
보고서"→"소유"+"상황"+"보고서"처럼 알아서 올바르게 복합 분해해준다는 걸
확인했다 — 미래에 DART가 새 보고서 유형을 추가해도 사전을 매번 늘릴 필요가
없다는 뜻.

**교훈**: 한국어 형태소 분석기는 "설치하면 끝"이 아니라 **도메인 사전 튜닝이
필수**다. 일반 목적 사전은 일상 어휘 기준으로 만들어져서 특정 도메인(여기서는
금융/법률 공시 용어)의 핵심 단어를 놓치거나 잘못 분해할 수 있고, 그게 검색
불가라는 형태로 조용히 나타난다. 코드를 짜기 전에 실제 도메인 텍스트로
`_analyze` API를 먼저 돌려보는 습관이 이번처럼 결정적인 문제를 사전에
잡아낼 수 있다.

### 2-9. 재무 수치가 조밀한 서술형 청크는 BM25도 벡터 검색도 놓친다 — 하이브리드로도 안 커버되는 구간

하이브리드 검색 엔진 검증 단계에서(2026-07-23) "의미 지향" 질의로 일부러 정확한
용어를 피해봤다: "기도산업이 최근 은행 등에서 빌린 돈의 규모는 어떻게
변화했나요?"("차입금"이라는 단어를 안 쓰고 "빌린 돈"으로 패러프레이즈).

미리 확인해둔 정답 청크(id=3220, 총차입금 규모가 2023년말 370억원→2024년말
788억원→2025년말 906억원으로 증가한다는 내용)가 **BM25 top 10에도, 벡터 검색
top 200(전체 5,201건 중)에도 안 들어왔다**:

- **BM25가 못 찾은 이유**: 질의의 "빌린 돈"과 원문의 "차입금"이 형태소 수준에서
  전혀 안 겹친다 — 동의어지만 다른 단어라 역색인 매칭이 원천적으로 불가능하다.
  이건 예상된 한계다(BM25는 애초에 정확 매칭 기반).
- **벡터 검색이 못 찾은 이유가 더 흥미롭다**: 이 청크는 정규식 폴백으로 망가진
  청크가 **아니다** — `chunk_source=SECTION`, `chunk_type=TEXT`, `section_title=
  요약정보`로 청킹 자체는 정상이고, 내용도 문법이 온전한 서술형 문단이다("유동비율은
  2023년말 209.2%에서... 이는 해외 생산시설 확충 조달을 위한 대규모 외부 차입을
  단행했기 때문입니다" 등). 그럼에도 임베딩이 질의와 충분히 가깝게 못 담았다.
  가능한 원인 두 가지를 구분해서 열어둔다(아직 검증 안 됨):
  1. 문장 안에 비율/금액 수치(209.2%, 370억원 등)가 조밀하게 섞이면 임베딩이
     서술적 의미보다 숫자 토큰에 더 끌려가 문장 전체의 "의미"가 흐려질 수 있다.
  2. 질의 프레이밍 자체의 문제 — "은행 등에서 빌린"이라는 표현이 원문에 없는
     프레임(원문은 "해외 생산시설 확충을 위한 외부 차입"이라는 맥락)이라 안
     맞았을 수도 있다.

**`SLIDING_WINDOW`(2-5, 2-7, progress.md 3절 1번) 이슈와 원인은 다르다** — 헷갈리지
않게 명확히 구분해둔다. `SLIDING_WINDOW`는 정규식 폴백이 구조 정보(섹션 마커,
표 라벨-값 관계) 자체를 잃어버리는 **청킹 메커니즘 결함**이고, 이번 건은 청킹은
멀쩡한데 **임베딩/질의가 재무 수치 조밀 텍스트를 잘 못 담는** 별개의 현상이다.
다만 두 문제 다 "재무 수치가 많이 들어간 콘텐츠는 검색 관점에서 약하다"는 같은
증상의 다른 얼굴이라는 점에서 나중에 같이 검토할 가치는 있다.

**의미**: 이 조합(패러프레이즈 어휘 + 수치 조밀 문장)은 지금 하이브리드 검색
구조(BM25 top-50 + 벡터 top-50 → RRF)로 **커버가 안 되는 사각지대**다 — 둘 다
후보군에도 안 들어왔으니 RRF가 아무리 잘 융합해도 답이 없다. RRF 자체의 결함이
아니라 후보 생성 단계의 한계다.

**향후 검토 방향(결정 안 함, 옵션만 기록)**:
- 재무 수치가 많은 청크에 한해 숫자를 텍스트로 정규화(예: "370억원" 앞뒤에 맥락
  문구를 추가)하거나, 표 형태로 재구성해 임베딩이 수치와 항목명을 더 명확히
  연결하게 하는 방법
- 청크에 요약 문장을 앞에 붙여 임베딩이 "이 청크는 000에 대한 내용"이라는
  신호를 더 강하게 받게 하는 방법(청크 재구성 필요, 비용 발생)
- 질의 확장(query expansion) — 사용자 질의에 동의어(차입금≒빌린 돈)를 추가해
  BM25 재현율을 높이는 방법(구현 단순, 다만 도메인 동의어 사전을 또 만들어야 함)
- 그냥 현재 한계로 받아들이고, 실사용 질의 로그를 보면서 실제로 이런 유형의
  질의가 자주 나오는지 먼저 관찰한 뒤 재검토(YAGNI 관점에서 제일 저렴한 선택지)

### 2-10. 같은 문구가 여러 공시(또는 한 공시 안에서도 여러 곳)에 반복 등장한다 — Top-K가 중복으로 채워지는 문제

`/search` 화면(RRF 시각화)을 만들다가 사용자가 직접 발견했다(2026-07-23): "신영증권의
증권발행실적보고서 내용은?" 질의의 top-4가 회사명/대표이사/주소/전화 같은 표지
정보로 거의 동일했다. 코드 수정 전에 먼저 DB를 직접 조회해 규모와 원인을
확인했다.

**규모**: 전체 `chunks` 5,201건 중 **1,003건(19.3%)**이 다른 청크와 content가
완전히 동일(md5 기준)했다. 이 중 651건(65%)이 500자 이상이라, 사소한 헤더
중복이 아니라 실질적인 정보 손실 규모였다.

**원인 — 청킹 버그가 아니라 원본 데이터 특성**: 중복 청크 1,003건 **전부**
`chunk_source=SECTION`이었다(`SLIDING_WINDOW`는 0건). 오버랩 알고리즘 버그라면
`SLIDING_WINDOW`에서 나와야 하는데 전혀 없었다 — 이 데이터 하나로 "청킹
메커니즘 결함"이라는 가설을 배제할 수 있었다. 실제 원인은 공시 업무 관행이
만드는 3가지 반복 패턴이었다:

1. **같은 공시 내부 반복**(322개 청크, 120그룹) — 메리츠증권 일괄신고추가서류
   1건(`rcept_no=20260721000066`) 안에 채권 여러 회차가 포함돼 있고, 각
   회차마다 동일한 규제 문구("Ⅶ. 그 밖에 투자자보호를 위해 필요한 사항")가
   반복 삽입된다. `chunk_index`가 정확히 68 간격(70/138/206/274)으로
   반복돼 회차 단위 반복임을 확인했다.
2. **같은 회사, 다른 공시 간 반복**(138그룹) — 신영증권이 같은 날 채권
   회차별로 별도 공시 4건(`rcept_no` 79/84/99/109)을 제출했는데, 표지·절차
   안내 섹션이 서식상 거의 동일하다. 이 중 3건(`93`/`95`/`101`)은 표지
   청크(`chunk_index=0`)가 md5까지 완전히 같았다.
3. **여러 회사에 걸친 반복**(52그룹, 대부분 15~50자) — DART 표준 서식이
   강제하는 짧은 섹션/표 헤더("1. 발행회사에 관한 사항" 등)라 회사 무관하게
   문구가 동일하다. 정보량은 거의 없는 수준.

**대응 — "완전 일치"만 중복으로 본 이유**: `HybridSearchService`에 RRF 융합
직후(content를 hydrate한 뒤, top-K로 자르기 전) content 정규화(공백만 축약)
후 완전 일치 여부로 대표 청크 하나만 남기고 나머지는 `duplicateSources`로
보존하는 로직을 추가했다(`hybrid-search.dedup.enabled`로 토글).

날짜만 다른 "사실상 중복"(신영증권 4위 사례, "2026년 07월 20일" vs "07월
21일")까지 잡을지 고민했지만 **의도적으로 배제**했다 — 하필 "Ⅳ. 조달된
자금의 사용내역" 같은 섹션은 회차마다 실제로 다른 금액이 적힌 **진짜 다른
정보**라서, 날짜/숫자를 무시하는 정규화를 넣으면 "500억원"과 "300억원"이
적힌 서로 다른 회차를 같다고 오판할 위험이 있다. 금융 도메인에서 이런
오판은 출처 명시라는 핵심 가치와 직접 충돌하는 정보 왜곡이다. 완전 일치
기준만으로도 신영증권 top-4 중 3개(75%)가 걸러져 실효성은 충분했고,
오탐(false positive) 위험은 0에 가까웠다.

**실측 효과 — `/answers` 전후 비교(같은 질의, 실 LLM 호출로 검증)**:

| | dedup=false(기존) | dedup=true(적용 후) |
|---|---|---|
| 답변 | "회사명: 신영증권 주식회사 / 대표이사: 금정호 / 본점 소재지: ... [1]" (표지 정보만) | "회사명: 신영증권 주식회사 / 대표이사: 금정호 / ... [1][2]. 또한, 조달된 자금의 사용내역도 포함되어 있으며, 신영증권 플랜업 제12772회 파생결합증권의 모집 또는 매출총액은 68,100,000원... [10]" (표지 + **실제 재무 정보**) |
| 노출 출처 | 1건 | 3건 |
| 입력 토큰 | 4,837개 | 3,558개 |
| 비용 | $0.000901 | $0.000669 |

원인은 명확하다 — 기존엔 top-10 컨텍스트 슬롯 중 4개가 똑같은 표지 정보로
낭비돼서, 모델이 실제 재무 내용(조달된 자금의 사용내역)을 애초에 볼 기회가
없었다. "Top-K에 중복이 섞이면 실질 정보량이 준다"는 우려가 추측이 아니라
**실측으로 확인된 품질 저하**였고, 중복 제거 후 같은 질의에서 진짜 재무
정보가 답변에 포함됐다 — 입력 토큰이 줄면서 비용도 함께 낮아졌다(중복
텍스트가 프롬프트에서 빠졌기 때문).

**회귀 없음 확인**: 애초에 중복이 없던 질의(GRT 유상증자, 파라택시스코리아
합병)는 `/search` top-10이 dedup 전후로 완전히 동일했다(순위/RRF 점수 1도
안 바뀜) — 중복이 있는 질의에서만 효과가 나타나고 다른 질의는 건드리지
않는다는 것도 실측으로 확인했다.

**설계 결정 — 색인 단계가 아니라 검색 결과 후처리 단계에서 제거**: 원본
저장(ES/pgvector)은 그대로 두고 `HybridSearchService`가 RRF 융합 후
`content` 기준으로 대표 청크만 추리는 방식을 택했다. 색인 단계에서 아예
중복을 제거하는 대안도 검토했지만, 그러면 "청크 1개 = 공시 1개"라는 현재
관계가 깨지고 대표 청크 하나만 남았을 때 "이 문구가 정확히 어느 공시에서
왔는지"가 모호해진다 — 출처 명시라는 이 프로젝트의 핵심 가치와 충돌 소지가
있어 보류했다. 대신 제거된 출처는 버리지 않고 `duplicateSources`에 보존해
`/search` 화면에서 "관련 공시 N건"으로 펼쳐볼 수 있게 했다(DART 링크 포함,
출처는 하나도 숨기지 않음).

### 2-11. corpCode.xml 실측 — corp_cls 없음, stock_code는 공백 1개, corp_name은 유일하지 않음

2026-07-26, 회사 목록 확대(corpCode.xml 적재) 설계 단계에서 실제로 한 번 받아 구조를
확인했다. 마이그레이션/파싱 로직을 짜기 전에 실물부터 본다는 원칙 그대로다.

**받는 방법**: `GET https://opendart.fss.or.kr/api/corpCode.xml?crtfc_key={API_KEY}`.
document API와 마찬가지로 ZIP으로 온다(3.6MB) — 안에 `CORPCODE.xml` 파일 하나(30MB,
UTF-8)가 들어있다. list/document API와 달리 페이징 파라미터가 없다 - 등록된 회사
전체를 한 번에 스냅샷으로 준다.

**XML 구조** — document API의 `dart4.xsd` 스키마와 전혀 다른 단순 목록형이다:
```xml
<result>
  <list>
    <corp_code>00434003</corp_code>
    <corp_name>다코</corp_name>
    <corp_eng_name>Daco corporation</corp_eng_name>
    <stock_code> </stock_code>
    <modify_date>20170630</modify_date>
  </list>
  <!-- 118,535건 반복 -->
</result>
```
`xml.etree.ElementTree`(엄격 파서)로 에러 없이 전체가 파싱됐다 — document API 원문
(2-2, 2-5, 2-7)과 달리 이 파일은 애초에 well-formed라 관대한 파싱/폴백이 필요 없다.

**전체 건수**: 118,535건. `corp_code` 전부 8자리 숫자 문자열이고 완전히 고유(중복 0건) —
설계 단계에서 전제한 "corp_code만이 신뢰할 수 있는 키"가 실측으로도 확인됨.

**`corp_cls` 필드가 정말로 없다** — 설계 단계에서 예상한 대로다. corpCode.xml에는
법인구분(Y/K/N/E)이 아예 없고, list API 응답에만 존재한다. `companies.corp_cls`를
nullable로 바꿔야 한다는 결정이 실물로 확정됨.

**`stock_code` 빈 값의 정확한 형태 — 공백 문자 정확히 1개**(`" "`, `len=1`). 8칸
공백이 아니었다 — 파싱 시 `.strip()` 결과가 빈 문자열이면 `null`로 저장하면 된다.
118,535건 중 종목코드가 채워진(비상장이 아닌) 건 3,979건(3.4%)뿐이고, 전부 6자리
숫자였다. (참고: 3,979건은 흔히 알려진 코스피+코스닥+코넥스 합계 약 2,500개보다
많다 — 우선주 등 별도 종목코드를 갖는 종목이나 상장폐지 이력까지 섞여 있는 것으로
추정되나, 이번 설계에는 영향이 없어 더 파고들지 않았다.)

**`corp_name`**: 길이 1~73자(`VARCHAR(255)`로 충분). 특수문자는 실제 상호에 흔한
것들(`. ) ( , & - : · / ' +` 등)만 나왔고 위험한 문자(`<`, `>`, 제어문자)는 없었다.
**예외 1건**: 회사명에 탭 문자가 섞여 있었다(`"상해신남양앙리교육과기지분유한공사\t"`)
— 파싱 시 trim이 필요하다는 뜻.

**`corp_name`은 유일하지 않다** — 5,516개 이름이 2건 이상 중복돼(총 13,382행) 전체의
11.3%가 동명이인이다. corp_name으로 회사를 매칭/병합하면 절대 안 된다는 걸 재확인.

**기존 DB(1,044개 회사, 2026-07-26 기준 - 스케줄러가 계속 돌아 3단계 완성 시점의
558건보다 늘어난 상태)와 대조**: corp_code 기준으로 전체가 corpCode.xml에 그대로
존재했다(누락 0건, stock_code 불일치도 0건). **`corp_name` 불일치를 1건 발견했다**
(`corp_code=01065013`: 기존 DB "우정바이오" ↔ corpCode.xml "콜마바이오텍") — 실제
상호변경으로 보이며, "corp_name/stock_code는 corpCode.xml 값으로 덮어쓴다"는 설계
결정이 실익이 있다는 걸 실측 사례로 증명했다.

`modify_date`는 8자리(`YYYYMMDD`) 고정, 최댓값이 `20260724`(실측일 이틀 전)라 DART가
최근까지 계속 갱신하는 살아있는 데이터임을 확인했다.

### 2-12. "미리 최적화"가 실측에서 뒤집힌 사례 — pg_trgm GIN 인덱스가 자동완성에 도움이 안 됨

2026-07-27, corpCode.xml 확대(118,535건 적재) 직후 회사명 자동완성 성능을 검증하다가
발견했다. 설계 단계에서는 "10만 건 규모의 `LIKE '%q%'` 검색은 인덱스 없이는 느려질
것"이라는 추론만으로 `pg_trgm` GIN 인덱스(`idx_companies_corp_name_trgm`)를 먼저
추가했는데(V4), 실측 결과 세 가지 이유로 이 판단이 틀렸다는 게 드러났다.

**원인 1 — Spring Data JPA `ContainingIgnoreCase`가 `upper()`로 감싼다**: 실제 Hibernate
SQL 로그(`logging.level.org.hibernate.SQL: DEBUG`로 일시적으로 확인)를 보면 다음과 같이
생성된다.
```sql
select ... from companies where upper(corp_name) like upper(?) escape '\' order by corp_name fetch first ? rows only
```
인덱스는 `corp_name` 원본 컬럼에 걸려 있는데, predicate는 `upper(corp_name)`이라는 별개의
표현식이다. `EXPLAIN ANALYZE`는(`enable_seqscan = off`로 강제해도) 항상 Seq Scan을
선택했다 — 이 predicate와 매칭되는 인덱스 기반 플랜 자체가 존재하지 않는다는 뜻이다.
```
Seq Scan on companies (actual time=0.012..25.996 rows=275 loops=1)
  Filter: (upper(corp_name) ~~ '%삼성%')
  Rows Removed by Filter: 118260
Execution Time: 27.969 ms
```

**원인 2 — 한글 단문 검색은 trigram 선택도가 낮다**: `upper()` 없이 순수 `corp_name
ILIKE '%삼성%'`로 바꾸면 인덱스가 기술적으로는 매칭되지만(`enable_seqscan=off`로 강제
시 `Bitmap Index Scan on idx_companies_corp_name_trgm` 확인됨), 후보로 119,200건(전체
118,535건과 맞먹는 규모)을 반환한 뒤 118,260건을 재확인(recheck) 단계에서 걸러냈다.
"삼성" 같은 2글자 한글 검색어는 trigram(3글자 단위 조각) 개수 자체가 너무 적어 후보를
거의 못 좁힌다는 뜻이다. 결과적으로 강제 인덱스 스캔이 **214.705ms로 Seq
Scan(27.969ms)보다 7배 이상 느렸다** — 플래너가 자동으로 Seq Scan을 고른 게 우연이
아니라 실제로 더 합리적인 선택이었다.

**원인 3 — 118,535건 규모에서 Seq Scan 자체가 이미 충분히 빠르다**: `upper()` 버전
27.969ms, 순수 `ILIKE` 버전 42.568ms(강제 없이 자연 선택 시) — 자동완성 UX 기준으로
체감 지연이 없는 수준이다.

**대응**: `idx_companies_corp_name_trgm` 인덱스를 Flyway V5로 제거했다. "안 쓰이는데
존재하는" 인덱스는 쓰기 비용만 발생시키고, 나중에 코드를 보는 사람이 "이 인덱스가 왜
있는데 안 쓰이지"라고 혼란스러워할 여지만 남기기 때문이다. `pg_trgm` 확장 자체는
유지했다 - 설치 비용이 없고, 나중에 실제로 유효한 패턴(더 긴 검색어, 영문 회사명,
다른 컬럼 등)이 실측으로 확인되면 인덱스만 다시 추가하면 된다.

**교훈 — "확정된 문제"라고 판단해 미리 최적화한 것이 실측에서 뒤집힌 사례**: 이
프로젝트가 지금까지 지켜온 원칙("먼저 실측하고 그 근거로 설계한다" - Nori 사전을
`_analyze` API로 먼저 테스트한 2-8, HNSW 인덱스를 `EXPLAIN`으로 실측 검증한 하이브리드
검색 사례 등)의 **반대 방향** 사례로 남겨둔다. 참고로 HNSW 인덱스는 지금은 플래너가
안 쓰지만 predicate 자체는 유효하게 매칭되고(`<=>` 연산자로 정렬 시 강제하면 정확히
잡힘) 데이터가 늘면 자연히 쓰이게 될 "아직 이른" 케이스인 반면, 이번 `pg_trgm`은
(a) 실제 쿼리(predicate)와 애초에 안 맞고 (b) 설령 맞춰도 도메인 데이터(한글 단문
검색어) 특성상 선택도가 낮아 오히려 손해라는 점에서 성격이 다르다 - "나중엔 쓰일
인덱스"가 아니라 "이 형태로는 앞으로도 안 쓰일 인덱스"였다. "10만 건 LIKE 검색은
느릴 것"이라는 추론이 그 자체로는 합리적으로 보였지만, (a) ORM이 실제로 생성하는
SQL의 정확한 형태, (b) 도메인 데이터(한글 단문 검색어)의 실제 특성, (c) 이 데이터
규모에서 Seq Scan의 실제 속도라는 세 가지 - 전부 실측 없이는 알 수 없는 요인이었다.
**인덱스는 "느릴 것 같다"는 추론이 아니라 실제 쿼리 로그 + `EXPLAIN ANALYZE`로
필요성을 확인한 뒤에 추가해야 한다** - 나중에 비슷한 최적화를 고려할 때 이 사례를
먼저 참고할 것.

## 3. 청킹 전략 제안 (RAG용)

1. **문서 유형(`report_nm`)별로 처리 전략을 분기한다.**
   소유상황보고서류처럼 원문이 작은(수백~수천 자) 문서는 통째로 1개 청크로 넣어도 충분하고,
   투자설명서·사업보고서류처럼 큰(수만~수십만 자) 문서는 아래 2, 3번 전략이 필요하다.

2. **1차 분할은 구조 기반(섹션 단위)으로 한다.**
   문서 안에 법정 서식이 정한 번호 붙은 섹션(`TITLE`, 예: "1. 발행회사에 관한 사항",
   "2. 보고자에 관한 사항")이 이미 존재한다. 이 경계로 먼저 나누면 "보고자가 누구야?" 같은
   질의에 관련 섹션만 정확히 걸리는 청크를 만들 수 있다. 고정 길이로만 자르면 섹션이 중간에
   잘려 검색 품질이 떨어질 위험이 크다.

3. **섹션이 너무 크면 2차로 토큰/문자 기반 슬라이딩 윈도우를 적용한다.**
   리스크 고지문처럼 서술형 섹션 하나가 수천 자를 넘는 경우, 섹션 내부에서 다시
   500~1,000자(또는 토큰) 단위 + 100~150자 오버랩으로 분할한다.

4. **표는 "라벨: 값" 형태로 직렬화해 청크에 포함한다.**
   표를 억지로 잘게 쪼개면 라벨과 값이 서로 다른 청크에 들어가는 최악의 경우가 생긴다.
   표 하나를 통째로 유지하거나 소속 섹션에 붙이고, 셀을 flatten하지 말고 행 단위로
   `"회사명: 주식회사 큐리오시스"`처럼 재구성해서 넣는다.

5. **파싱은 실패를 전제로 방어적으로 구현한다.**
   §2-2에서 확인했듯 일부 문서는 엄격한 XML 파서로 파싱되지 않는다. 관대한 파서(`lxml recover=True`)
   또는 정규식 폴백을 반드시 준비한다.

  `char_length` 임계치(2,000자)로 분기한다. `report_nm`은 `[기재정정]` 접두어 등
  표기 변형이 많아 문자열 매칭이 쉽게 깨진다.
- **2번(구조 기반 분할)** — §2-5에서 확인했듯 `raw_content`에 항상 구조 정보가
  남아있는 게 아니라서(정규식 폴백 경로는 마커가 없음), `[[SECTION]]` 마커 유무로
  먼저 분기하고 있을 때만 구조 기반 분할을 적용한다. 어떤 경로로 만들어진
  청크인지는 `chunks.chunk_source`(`WHOLE_DOCUMENT`/`SECTION`/`SLIDING_WINDOW`)로
  구분해 나중에 방식별 검색 품질을 비교할 수 있게 했다.
